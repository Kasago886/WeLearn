### 2.7 P6 · 接入层通用化

| 项 | 内容 |
| --- | --- |
| 目标 | 接入层按 OpenAI 兼容协议工作，可指向任意兼容服务；DeepSeek 专有能力改为可选项 |
| 范围 | `app/infra/llm/`（档案、协议、客户端）、设置与表结构、计价、前端设置页；**不动**学习流程 |
| 出口条件 | 两种接口类型的请求/响应行为各有测试；设置/健康/余额按类型给出正确结果；老库升级后行为不变；真实 HTTP 验证通过 |

**关键取舍**：默认 `provider = deepseek`。理由不是偏好，而是"升级不得悄悄改变行为"——
默认切到通用档案会让思考开关、缓存统计与余额在升级后失效，而用户只会觉得"怎么变笨了"。

## 4. 缺陷档案

按发现阶段归档。**编号不跨阶段复用**；"何时发现"比"何时修复"更能说明测试是否有效。

### 4.1 P1 时期遗留、P3A 期间修复

| # | 问题 | 影响 |
| --- | --- | --- |
| 1 | **模型只输出思维链、正文为空时被当成"成功"**：客户端重试判据用的是"是否产出过任何增量"（思维链也算），执行器又对空正文无条件提交，于是 `content=""` 被落库、接口返回 200 | 用户在测评页提交回答后**界面毫无反应**——没有下一个问题、也没有任何报错，看着像卡死。真实观测 `completion=411 reasoning=411`、`max_tokens` 远未用满；同一批 53 次调用里出现 3 次（约 6%）。结构化输出通道（JSON）早有这条防护，流式通道一直漏着 |
| 2 | **测评的一轮不是原子的**：作答与轮次计数都在调用模型之前就落库，失败也不回退 | 失败后对话最后一条变成用户的作答，而 `pending_question` 正是由"最后一条 assistant 消息"推出来的，于是它变成 `null`、前端提交按钮点不动。光修 #1 只会把"静默死路"变成"会报错的死路" |

**修法**：把重试判据从"任何增量"改为"**正文**"，新增 `empty_content` 可重试错误；执行器再加一道
"组装后正文为空（含纯空白）绝不入库"的守卫；测评的作答与轮次计数推迟到整轮成功之后，
失败用 `Memory.snapshot()` / `replace_with()` 整体回退。回归测试共 9 个（客户端 3 + 执行器 3 + 接口 1 + 测评服务 2），
且已验证它们在回退守卫后**确定性失败**。

## 5. Spike 实测结论（2026-10-11，真实额度，`deepseek-flash`）

完整报告见 [Spike 实测结果](Spike实测结果.md)，工具为 `scripts/spike_real.py`。

| Spike | 结论 | 落地动作 |
| --- | --- | --- |
| A 结构化输出 | 生产配置下首次成功率 **88.9%**（9 次里 1 次 JSON 解析失败，长 JSON 更脆弱）；思考模式下 `max_tokens` 是**推理+正文的总预算**（推理占输出 60%~82%），压到 2048 会凭空制造"空内容" | 保持默认 `max_tokens=8192`；确认"必须显式设置 `max_tokens`"与"重试时翻倍"；设置页提示调小预算的后果 |
| B 判定质量 | 一致率 75% → **88%**（修正提示词后）；**放水 0 次**、**注入成功 0 次** | 提示词补两条：`pass` ⇒ `missing_points` 必须为空数组；润色意见不算缺失 |
| C 压缩收益 | 40 轮 → 压缩到 **3.0%**，关键信息 4/4 保留，耗时 2.0s | 保持阈值 40 轮 / 单次 10 轮；本地数据偏重重复，3.0% 是乐观值 |
| D 思考档位 | 判定任务三档位下**结论完全一致**、延迟几乎相同（1.6~1.9s）；教学讲解在 `max` 下推理翻倍、耗时 +60% | 默认 `high`；`max` 留作可选；设置页说明"关思考时档位无效" |

**测量方法的教训**：第一次跑 Spike A 时把 `max_tokens` 压到 2048，得到"首次成功率 55.6%、大量空内容"，
差点把"预算不足"误判成"官方不稳定"。**测某个变量时其它参数必须与生产一致**，
并且要能区分失败成因——第二次实测因此增加了"输出是否顶到上限"这一列。

**需真实额度才能验证的部分**：模型的注入拒绝率、判定误判率、JSON Output 空内容概率、压缩收益实测。
自动化测试锁住的是"链路上没有被带偏的入口"，不能替代对模型实际行为的抽样。

### 6.3 P5（10 项断言，2026-10-21，单进程交付形态）

这一轮不再用 vite 开发服务器，而是让后端托管 `web/dist`——被测的就是用户真正会打开的那个页面。

| 覆盖点 | 断言要点 |
| --- | --- |
| 交付形态 | `http://127.0.0.1:8100/` 由后端直接返回前端产物；深链接 `/subjects/{id}/teach` 刷新仍 200 |
| 窄屏（768px） | `document.scrollingElement.scrollWidth === 768`，无横向溢出 |
| 键盘可达 | Tab 依次可达链接、输入框、按钮，且 `outline-style` 为 `solid`（焦点环不是 `none`） |
| 状态表达 | 状态徽标带中文文字，颜色不是唯一信息载体 |
| 流式节流 | 60ms 合帧后正文末句仍在（验证 `finally` 里的强制 flush 生效，不会丢尾字） |
| 纯键盘作答 | 只在输入框用 `keyboard.type` 打字 + Tab 到提交按钮 + Enter，判定通过并标记「已掌握」 |
| 运行期健康 | 全程无 `pageerror` |

**顺带的方法论修正**：`locator.focus()` 触发的焦点在 Chromium 下不一定命中 `:focus-visible`
（脚本聚焦不继承"键盘操作"标记），用 `focus()` 断言焦点环会得到假阴性；改为真的按 Tab 走一遍。

## 7. 测试性能优化记录

早期全套 149s，其中 **94% 是夹具装卸，不是测试逻辑**（真正跑断言的部分只有 9s）。

| 开销 | 单次 | 根因 | 处理 |
| --- | --- | --- | --- |
| `build_context` 装配 SSL 上下文 | 0.318s | `httpx.AsyncClient()` 默认每次构造都重新解析 CA 证书包 | `client.py` 用 `lru_cache` 复用 `httpx.create_ssl_context(verify=True)` 的结果 → 0.040s |
| `QueueLogger.close()` | 0.110s | `flush()` 里固定 `sleep(0.05)` 等沉降 + `join()` 等后台线程 0.1s 取队超时 | `flush()` 改用 `queue.unfinished_tasks` 精确判定；`close()` 投哨兵叫醒线程 → 0.008s |

两者都是生产代码的净收益（进程启动少 0.4s，设置页"测试连接"不再重解析证书包）。
顺带修掉一个隐患：旧 `flush()` 拿"队列空"当判据，而后台线程是**先取条目、再落盘**的，
所以它会**虚报成功**；`test_flush_is_a_real_barrier` 专门锁住这条（旧实现下确定性失败）。

**教训**：一批测试跑得慢时，先按 `setup / call / teardown` 分桶量一遍再动手。
"哪个用例慢"和"每个用例固定付多少"是两件事，后者才是大头，而它在逐用例列表里根本看不出来。
