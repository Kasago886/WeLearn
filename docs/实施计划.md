## 1. 规划原则

| # | 原则 | 为什么 |
| --- | --- | --- |
| 1 | **记忆 + Agent 内核先做** | 测评 / 路径规划 / 教学 / 判定 / 压缩五处共用同一套"一轮对话"机制，是全项目最大复用点；先做可避免五遍重复实现 |
| 2 | **契约先冻结再动前端** | SSE 事件类型、四类结构化输出 JSON schema、数据库表结构，三者未冻结就写前端必然返工 |
| 3 | **状态机早立** | 会话状态与"待回答的检查点"必须落库（FR-410），后期补做等于重构 |
| 4 | **质量风险靠实测而非猜测** | 结构化输出稳定性、判定是否放水、压缩是否真省 token、思考档位取舍，四项必须先用 Spike 量化（见第 5 章） |
| 5 | **失败路径与成功路径同批实现** | FR-610（失败不污染记忆）、FR-712（错误分类）、FR-716（空内容/截断）都是失败路径，若留到最后补救会撼动内核 |
| 6 | **每个阶段可独立演示** | 每阶段结束必须能在 UI 或日志上看到实质进展，避免"三周无可见产出" |

## 5. 建议先行的技术验证 Spike

全部安排在 P1 内完成，结论直接落为配置默认值与提示词定稿，避免后期返工。

| Spike | 要回答的问题 | 结论用途 | 建议时机 |
| --- | --- | --- | --- |
| A · 结构化输出实测 | JSON Output 返回空 `content` 的实际概率？截断率与 `max_tokens` 取值的对应关系？ | 定 FR-716 的重试次数、默认 `max_tokens`、是否需要提示词瘦身 | T1.5 之前 |
| B · 判定质量抽测 | 用 20 组"完整正确 / 部分正确 / 错误"作答样本喂给判定提示词，误判率多少？ | 定判定提示词强度；决定是否需要"判定 + 自查"双通道（会使成本翻倍，需谨慎） | T1.6 之前 |
| C · 压缩收益实测 | 压缩前后 prompt tokens、缓存命中率、回答质量的变化？ | 定 FR-604 的默认阈值（初值 40）与单次压缩轮次（初值 10） | T1.4 期间 |
| D · 思考档位实测 | `deepseek-flash` / `deepseek-v4-pro` × `effort=low/high/max` 对教学文本质量与首 token 延迟的影响 | 定 FR-703 各用途的默认模型与档位（初值：规划/判定用 V4-Pro + high，压缩关闭思考） | T3.5 之前 |

## 7. 验证策略

| 层次 | 手段 | 覆盖范围 |
| --- | --- | --- |
| 单元测试 | pytest + 注入桩 LLM（对应 ReferenceCode 的 `ILlmService` 设计） | 状态机、判定解析、压缩签名校验、路径生成解析、配置回退、路径越界、SSE 解析 |
| 契约测试 | 用 T0.7 录制的真实响应夹具回放 | 空 `content`、截断 JSON、429、`: keep-alive`、连接关闭 |
| 集成测试 | 本地空跑（不调真实 API）+ 假 SSE 服务 | 一轮对话、工具调用累积、压缩后台执行 |
| 端到端 | 真实 API 跑一个主题的完整闭环（人工执行，脚本半自动） | 全流程可用性、延迟体感、费用观察 |
| 全量回归 | P5 按 AC-01~AC-33 逐条执行 | 交付验收 |

**成本控制建议**：日常开发默认使用桩与夹具；仅在 T2.5、T3.3、T5.6 三种场景使用真实 API，并开启用量统计观察。

**测试时长**：全套 534 个用例约 29s。这里有一条踩过的坑值得记下来：早期全套要 149s，
而其中 **94% 是夹具装卸，不是测试逻辑**（真正跑断言的部分只有 9s）。

| 开销 | 单次 | 根因 | 处理 |
| --- | --- | --- | --- |
| `build_context` 装配 SSL 上下文 | 0.318s | `httpx.AsyncClient()` 默认每次构造都重新解析 CA 证书包 | `client.py` 用 `lru_cache` 复用 `httpx.create_ssl_context(verify=True)` 的结果；取值方式仍复用 httpx 的公开工厂，不抄它的内部逻辑 → 0.040s |
| `QueueLogger.close()` | 0.110s | `flush()` 里固定 `sleep(0.05)` 等沉降 + `join()` 等后台线程 0.1s 取队超时 | `flush()` 改用 `queue.unfinished_tasks` 精确判定；`close()` 投一个哨兵值叫醒线程 → 0.008s |

两者都是生产代码的净收益（进程启动少 0.4s，设置页每次"测试连接"不再重解析证书包）。
顺带修掉一个隐患：旧 `flush()` 拿"队列空"当判据，而后台线程是**先取条目、再落盘**的，
所以它会**虚报成功**；`test_flush_is_a_real_barrier` 专门锁住这条（该用例在旧实现下确定性失败）。

**教训**：一批测试跑得慢时，先按 `setup / call / teardown` 分桶量一遍再动手。
"哪个用例慢"和"每个用例固定付多少"是两件事，后者才是大头，而它在逐用例列表里根本看不出来。

**Spike 实测（2026-10-11，真实额度，`deepseek-flash`）**：完整报告见
[Spike 实测结果](Spike实测结果.md)，工具为 `scripts/spike_real.py`。

| Spike | 结论 | 落地动作 |
| --- | --- | --- |
| A 结构化输出 | 生产配置下首次成功率 **88.9%**（9 次里 1 次 JSON 解析失败，长 JSON 更脆弱）；思考模式下 `max_tokens` 是**推理+正文的总预算**（推理占输出 60%~82%），压到 2048 会凭空制造"空内容" | 保持默认 `max_tokens=8192`；确认"必须显式设置 `max_tokens`"（FR-716）与"重试时翻倍"是对症设计；设置页提示调小预算的后果（T3.5） |
| B 判定质量 | 一致率 75% → **88%**（修正提示词后）；**放水 0 次**、**注入成功 0 次** | 提示词补两条：`pass` ⇒ `missing_points` 必须为空数组；润色意见不算缺失。守卫保持不动（宁可不放行） |
| C 压缩收益 | 40 轮 → 压缩到 **3.0%**，关键信息 4/4 保留，耗时 2.0s | 保持阈值 40 轮 / 单次 10 轮；真实长会话的收益待 P3/P4 抽样（本地造的数据偏重复，3.0% 是乐观值） |
| D 思考档位 | 判定任务在三档位下**结论完全一致**、延迟几乎相同（1.6~1.9s）；教学讲解在 `max` 下推理翻倍、耗时 +60% | 默认 `high`；`max` 留作可选（T3.5）；设置页需说明"关思考时档位无效"（FR-718） |

**测量方法上的一条教训**：第一次跑 Spike A 时把 `max_tokens` 压到 2048，得到"首次成功率 55.6%、
大量空内容"，差点把"预算不足"误判成"官方不稳定"。**测某个变量时其它参数必须与生产一致**，
并且要能区分失败成因——第二次实测因此增加了"输出是否顶到上限"这一列。

**默认模型**：全部用途默认 `deepseek-flash`（`AppSettings.model_default` 的代码默认值与
`.env` 一致）；`RECOMMENDED_OVERRIDES`（判定/规划用 `deepseek-v4-pro`）保持**默认不启用**，
由 T3.5 决定是否开放。`tests/test_policy_and_usage.py::test_default_policy_inherits_global_settings`
锁住这条默认值。
