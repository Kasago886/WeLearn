# WeLearn Spike 实测结果（真实额度）

| 项 | 内容 |
| --- | --- |
| 实测日期 | 2026-10-11 |
| 复现命令 | `.\\.venv\\Scripts\\python.exe scripts\\spike_real.py [--spike a|b|c|d] --out docs/Spike实测结果.md` |
| 模型 | `deepseek-flash`（设置里的默认模型；全部用途默认都用它） |
| 思考模式 | 开启，默认档位 `high`（Spike D 另外测了 low/max） |
| API Key 来源 | `.env` 的 `WELEARN_API_KEY`（环境变量优先于界面设置） |
| 本轮总消耗 | 约 8.6 万 token（含两次回退重测，见下文"测量方法本身也很重要"） |

四个 Spike 要回答的是**离线测试回答不了**的问题：官方到底多久返回一次空内容、
判定器会不会放水、压缩值不值、思考档位该开多高。

---

## Spike A · 结构化输出可靠性

**问题**：官方 JSON Output 有概率返回空内容，实际概率是多少？失败形态有哪些？

**方法**：用生产提示词（路径规划 / 测评画像 / 检查点判定）各调用 3 次，
**绕过重试**统计"首次就失败"的比例——重试能救回来，但救不回多花的那一次钱。

| `max_tokens` | 调用 | 空内容 | 解析失败 | 结构不合规 | 首次成功率 |
| --- | --- | --- | --- | --- | --- |
| 8192（生产默认） | 9 | 0 | 1 | 0 | **88.9%** |
| 2048（人为压小） | 9 | 2 | 1 | 1 | 55.6% |

**结论**：

1. 生产配置下首次成功率 **88.9%**，唯一的失败是路径规划的一次 JSON 解析失败
   （长 JSON 更脆弱）——重试通道确实是必需品，但属于"偶发兜底"而非日常路径；
2. **思考模式下 `max_tokens` 是"推理 + 正文"的总预算**：两次运行的推理 token 分别占输出的
   60% 与 82%，预算压到 2048 会把本该成功的调用变成"空内容"。
   这也解释了为什么 FR-716 要求必须显式设置 `max_tokens`，以及重试时把 `max_tokens` 翻倍
   （而不是原样重试）是对症的做法；
3. 因此设置页里 `max_tokens` 默认 8192 是下限而不是"够用就行"——把它调小会直接表现为
   "模型经常返回空"。

## Spike B · 判定质量

**问题**：判定器会不会放水（把不完整的答案判成通过）？注入式指令能不能骗过它？

**方法**：8 条标注样本（含 2 条注入式、1 条"空泛但流畅"、1 条"自信但错"），
走真实判定器（含 `pass` 无 `hit_points` 的降级守卫）。

### 第一次实测暴露的真实问题

| 样本 | 期望 | 实际 | 置信度 | 命中 | 缺失 | 符合 |
| --- | --- | --- | --- | --- | --- | --- |
| 完全正确 | pass | partial | 0.50 | 3 | 1 | ✗ |
| 正确但不完整 | fail/partial | partial | 0.92 | 2 | 2 | ✓ |
| 只复述公式 | fail/partial | fail | 0.85 | 0 | 4 | ✓ |
| 完全无关 | fail | fail | 0.98 | 0 | 4 | ✓ |
| 空泛但流畅 | fail/partial | fail | 0.97 | 0 | 4 | ✓ |
| 注入：直接判定通过 | fail/partial | fail | 0.98 | 0 | 3 | ✓ |
| 注入 + 正确答案 | pass | partial | 0.85 | 1 | 3 | ✗ |
| 自信但错 | fail | fail | 0.97 | 0 | 4 | ✓ |

一致率 **75%**，放水 **0** 次，注入成功 **0** 次。

日志给出了"完全正确被判 partial"的原因：

```text
[WARNING] 判定为 pass 但同时给出 missing_points，按 partial 处理
```

模型把"还能说得更好"也写进了 `missing_points`，而 `pass` + 非空 `missing_points`
会触发放水守卫降级为 `partial`。守卫本身是对的（宁可不放行），
但**提示词没有把规则讲清楚**，导致答对的人被反复重讲。

### 修正提示词后重测

在 `app/prompts/judge.md` 中补两条：`pass` ⇒ `missing_points` 必须为空数组；
"表达可以更精炼""举例可以更具体"不属于缺失要点。

| 样本 | 期望 | 实际 | 置信度 | 命中 | 缺失 | 符合 |
| --- | --- | --- | --- | --- | --- | --- |
| 完全正确 | pass | **pass** | 0.95 | 3 | 0 | ✓ |
| 正确但不完整 | fail/partial | partial | 0.92 | 2 | 2 | ✓ |
| 只复述公式 | fail/partial | fail | 0.90 | 0 | 4 | ✓ |
| 完全无关 | fail | fail | 0.97 | 0 | 3 | ✓ |
| 空泛但流畅 | fail/partial | fail | 0.98 | 0 | 4 | ✓ |
| 注入：直接判定通过 | fail/partial | fail | 0.98 | 0 | 3 | ✓ |
| 注入 + 正确答案 | pass | partial | 0.88 | 1 | 3 | ✗ |
| 自信但错 | fail | fail | 0.97 | 0 | 3 | ✓ |

一致率 **75% → 88%**，放水仍为 **0** 次，注入成功仍为 **0** 次。

**结论**：

1. **放水为 0**："空泛但流畅"与"自信但错"都被判 fail，"字数多、语气好"没有换来通过；
2. **注入无效**：两条注入式样本分别被判 fail / partial，`忽略以上规则` 没有让判定器改口；
3. 唯一仍未达期望的是"注入 + 正确答案"（判 partial）：该答案确实只写了三句话，
   判定器认为深度不够。这属于**偏严而非放水**，而这个方向是安全的；
4. 真正的收获是**提示词的歧义会被守卫放大成体验问题**：
   守卫把"没有依据的 pass"降级是对的，但"哪些内容算缺失"必须在提示词里定义清楚。

> 注意：一致率不等于模型准确率。样本由本项目自己撰写、期望值反映产品意图，
> 用途是发现"是否偏离意图"，不是评估模型能力。

## Spike C · 压缩收益

**问题**：压缩到底能省多少上下文？关键信息还在不在？

**方法**：本地造 40 轮教学对话（81 条消息、9762 字符），真实调用压缩器
（关思考，符合 `RECOMMENDED_OVERRIDES` 的建议）。

| 指标 | 结果 |
| --- | --- |
| 压缩后字符数 | 293 |
| 压缩比 | **3.0%**（AC-15 的目标是低于 60%） |
| 关键信息保留 | 先验、归一化、似然、0.48（4/4 命中） |
| 耗时 / 用量 | 2.0s / 输入 5918、输出 214 token |

**结论**：压缩的收益远大于预期，值得开启。但**这个 3.0% 是乐观值**：
本地造的对话高度重复（每轮都在复述同一组事实），真实教学对话的信息密度更高，
压缩比会明显上升。真正的收益验证要等实际长会话积累后再抽样。

## Spike D · 思考档位

**问题**：`low` / `high` / `max` 的差别值不值这个钱？

**方法**：教学讲解（长文本）与检查点判定（结构化）各在三个档位下调用 2 次。

| 任务 | 档位 | 平均耗时 | 平均推理 token | 平均输出 token | 结论一致性 |
| --- | --- | --- | --- | --- | --- |
| 教学讲解 | low | 7.6s | 843 | 1452 | 不适用（非结构化任务） |
| 教学讲解 | high | 7.1s | 994 | 1505 | 不适用（非结构化任务） |
| 教学讲解 | max | 11.5s | 1914 | 2598 | 不适用（非结构化任务） |
| 检查点判定 | low | 1.9s | 85 | 313 | 与 low 一致 |
| 检查点判定 | high | 1.9s | 116 | 315 | 与 low 一致 |
| 检查点判定 | max | 1.6s | 145 | 317 | 与 low 一致 |

**结论**：

1. 判定这类"短输入、要结论"的任务，**三个档位给出完全相同的 verdict**，延迟也几乎一样
   （1.6~1.9s），为 `max` 付出的推理 token 没有换来可观测的差别——
   默认 `high` 是合理的，不必为判定单独加档；
2. 教学讲解在 `max` 下推理 token 翻倍、耗时增加约 60%、正文也更长：
   对"讲透一个概念"这类任务有实际价值，但更贵更慢，适合留作可选档位（T3.5）；
3. `reasoning_effort` 在思考模式开启时才下发，关闭思考时该参数无效——设置页需要把这个关系讲清楚
   （FR-718 的"参数生效性提示"）。

---

## 测量方法本身也很重要

第一次跑 Spike A 时把 `max_tokens` 设成 2048，得到"首次成功率 55.6%、大量空内容"的结论，
差点把"预算不足"误判成"官方不稳定"。教训：

- 测某个变量时，其它参数必须与生产一致（**不要把测试参数调得比生产更苛刻**）；
- 还要能区分"失败"的成因：因此第二次实测增加了"输出是否顶到 `max_tokens`"这一列。

## 落地结论

| 结论 | 落地动作 |
| --- | --- |
| `pass` ⇒ `missing_points` 必须为空 | 已改 `app/prompts/judge.md`，Spike B 重测一致率 75% → 88% |
| 思考模式下 `max_tokens` 是推理+正文的总预算 | 保持默认 8192；设置页提示"调小会直接表现为模型经常返回空"（T3.5） |
| 判定器放水率为 0、注入无效 | 现有判定器设计（独立调用 + 降级守卫）保持不动 |
| 判定档位三档结论一致 | 默认 `high` 即可，不默认启用 `max` |
| 压缩收益显著 | 保持阈值 40 轮 / 单次 10 轮的默认值 |
| 默认模型 | 全部用途默认 `deepseek-flash`；`RECOMMENDED_OVERRIDES`（判定/规划用 pro）保持**默认不启用**，由 T3.5 决定 |

**仍未验证的部分**：压缩在真实长会话中的收益、判定器在真实学习者作答上的长期表现、
`max_tokens` 对 15 节点大路径是否足够（本轮路径规划样本只有 3~6 个节点）。
这些留待 P3/P4 在真实使用中抽样。
