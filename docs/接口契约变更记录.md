## 2. 各版本变更摘要（原文）

### 2.1 v1.1（P2A）

1. 新增三个下行事件：`assessment`、`path`、`options`；
2. 节点位置字段统一为**从 1 开始**：`node_state.index`、路径里 `nodes[].index`、`current_index`；
3. 领域表（v2）与 `session_state.awaiting_decision`（v3）落地，`SCHEMA_VERSION = 3`；
4. HTTP 接口从"仅冒烟端点"扩展为完整接口清单。

### 2.2 v1.2（P3A）

1. 新增 `hint` 事件：告知前端"这是第几级提示"；
2. 路径编辑接口：改节点内容、插入、删除、移动、重生成单节点、整条重生成；
3. 教学深化接口：`teach/hint`、`teach/ask`、`teach/regenerate`；
4. `GET /teach/current` 增加 `last_action`，前端据此决定"重新生成"是否可点；
5. 表结构 v4：`message.kind`（自由提问标记）、`session_state.last_action`。

### 2.3 v1.3（空正文处理）

1. 新增错误分类 `empty_content`：模型只输出思维链、正文为空时算**可重试失败**，
   不再被当成"成功"（此前会落一条空回复并返回 200，界面看起来像卡死）；
2. 重试边界细化：判据从"是否产出过任何增量"改为"是否产出过**正文**"——
   思维链不算正文，因此只有思维链时仍可重试；
3. 测评的一轮改为**原子**：作答与轮次计数都在整轮成功后才落库，失败整体回退。
   否则失败后对话最后一条会变成用户的作答，而 `pending_question` 正是由"最后一条 assistant
   消息"推出的，于是它变成 `null`、提交按钮点不动——用户既看不到问题也重试不了。

### 2.4 v1.4（P3B 复习与档案）

1. 新增复习与档案共 8 个端点：`/review`、`/review/start`、`/review/answer`、
   `/nodes/{id}/history`、`PUT /nodes/{id}/note`、`/archive`、`/report`，并扩展 `/weak-points`；
2. `GET /teach/current` 增加 `review` 字段（FR-414）：正在"回顾上一节点"时前端要能说明
   "这次不是检查点作答"，否则用户会以为系统问错了题；
3. `answer_record` 与节点笔记增加 `source`（schema v5），前端据此区分
   "教学作答 / 复习作答"与"自动小结 / 手写笔记"；
4. 教学作答与复习作答**分开存**：复习不动 `current_node_id`，教学页与复习页互不干扰。

### 2.5 v1.5（P3C 模型策略与运维可见性）

1. 设置新增采样参数与模型策略：`temperature`、`top_p`（FR-718）、
   `audit_enabled`（FR-715）、`use_recommended_overrides` 与 `purpose_overrides`（FR-703），
   并新增只读的 `model_plan`——界面上的"选择"不等于生效，用户要看的是解析后的实际参数；
2. `GET /api/usage` 新增 `duration_ms`、`by_purpose`、`by_subject`、`cache_hint`（FR-705、FR-720）；
3. `GET /api/health` 新增可写性、日志、审计与用量摘要（FR-909），原有字段全部保留；
4. 表结构 v6：`app_settings` 增列；
5. `GET /assessment` 的 `transcript` 改为**任何状态都返回**（FR-208 的测评回放），
   `pending_question` 收紧为**仅测评进行中**非空——否则结束后最后一条画像结论
   会被当成待答问题，输入框会莫名重新打开。

### 2.6 v1.6（P4 增值能力）

1. 复习排期（FR-505、FR-506）：`GET /review` 增加 `due[]` / `due_count`；
   `GET /api/subjects` 每项增加 `due_reviews` / `needs_review`；
2. 成本与余额（FR-706、FR-710）：`GET /api/usage` 与 `GET /report` 增加 `cost`；
   新增 `GET /api/balance`（失败也返回 200，不阻塞主流程）；
3. 导出与检索（FR-805、FR-613、FR-803）：`GET /subjects/{id}/export`、
   `POST /subjects/import`、`GET /api/search`；
4. 运维（FR-903、FR-907）：`GET /api/logs`、`POST /api/logs/clean`、`GET /api/auth/verify`，
   以及可选的访问口令中间件（`X-Access-Token`，未通过返回 401）；
5. 表结构 v7：`knowledge_point.review_box` / `review_due_at` 与 `app_settings` 新增列；
6. 工具调用（FR-714）：请求体可携带 `tools`，**永不下发 `tool_choice`**；
   启用时历史 `reasoning_content` 必须回传。

### 2.7 P5 期间（无契约升版）

交付形态变化不改变接口，但补了一条**边界约定**（写进 [接口契约 §6.1](接口契约.md)）：
非 `/api` 路径由后端托管前端产物，未知前端路径回 `index.html`（SPA 深链接刷新不 404），
而 `/api/*` 的未知路径仍返回 `404 {"detail":"接口不存在"}`。

理由是这两件事看起来"都是 404"，实则不然：把 `/api/tpyo` 也回退成 HTML，用户看到的会是
"页面莫名加载成功"，排查时非常容易误判成"前端路由坏了"。契约版本因此保持 v1.6。

## 3. 表结构增量演进

`create_all` 只建缺失的表，**不会修改已存在的表**；因此 `app/infra/storage/db.py` 在 `init()`
里按 `SCHEMA_VERSION` 执行幂等的列级升级（先 `PRAGMA table_info` 检查，再 `ALTER TABLE ADD COLUMN`）。
以下为各版本新增的列及其理由。

### 3.1 v1（P0/P1）：基础表

`schema_version`、`app_settings`、`api_key_secret`、`conversation`、`chat_round`、`message`、`usage_record`。

### 3.2 v2（P2A）：领域表

`subject`、`session_state`、`assessment`、`assessment_level`、`learning_path`、`knowledge_point`、
`checkpoint`、`answer_record`、`weak_point`、`study_note`。

### 3.3 v3：`session_state.awaiting_decision`

表示"等用户三选一"。**必须落库**：否则刷新或重启后前端不知道作答通道已被关闭，用户会一直点提交。

### 3.4 v4（P3A）

| 表 | 列 | 用途 |
| --- | --- | --- |
| `session_state` | `last_action` | 最近一次教学动作（`explain` / `reteach:simpler` / `hint:2` / `reference`），供"重新生成上一条回复"知道该重跑什么（FR-413） |
| `message` | `kind` | 消息用途标记；`off_topic` 表示穿插提问（FR-411），用于把主线与随口提问分开 |

### 3.5 v5（P3B）

| 表 | 列 | 用途 |

## 4. 真实样本验证结论

### 4.1 录制事实（2026-10-10）

录制命令：`python scripts/llm_smoke.py --record`（模型 `deepseek-flash`，思考开启，`effort=high`）。
回放测试见 `tests/test_recorded_fixtures.py`。以下为当时实测确认的事实：

| # | 实测事实 | 对实现的影响 |
| --- | --- | --- |
| 1 | 数据块除 `choices` 外还带 `object` / `created` / `system_fingerprint`，`choices[0]` 还带 `logprobs` | 解析器只读 `choices[0].delta`，必须忽略未知字段（已满足） |
| 2 | 首块 `delta` 为 `{role:"assistant", content:null, reasoning_content:""}`，后续块也会出现空串 | 空串必须按"无增量"丢弃，否则会向前端推大量空事件（已满足） |
| 3 | 思维链与正文在 `delta` 中**交替**到达（本次 235 个思维链碎片、92 个正文碎片） | 前端需分别渲染两路增量；`reasoning` 与 `token` 事件不可合并 |
| 4 | 用量只在最后一个数据块出现：`prompt=40, cached=0, miss=40, completion=328, reasoning=235, total=368` | 收尾事件 `done` 必须携带该用量；首次调用的 `cached=0` 属正常（尚无缓存前缀） |
| 5 | JSON Output 返回 `{"answer": "..."}`，可用 `json.loads` 直接解析；关闭思考时 `reasoning_content` 为空串 | 结构化输出通道可行；空思维链按 `None` 处理 |
| 6 | `GET /models` 返回 `deepseek-flash`（DeepSeek-V4.1-Flash）与 `deepseek-v4-pro`，`context_window=1048576`、`max_output_tokens=393216`、`effort.supported_levels=[low,high,max]`、`default_level=high` | 与官方文档一致；设置页可据此渲染档位，不必写死（FR-702、FR-717） |
| 7 | `GET /user/balance` 返回 `is_available` 与 `balance_infos[]`，**金额是字符串**（如 `"17.39"`），币种为 `CNY` | FR-710 必须按字符串解析并按币种展示，不能强转数字 |
| 8 | 本次响应较快，**未出现** `: keep-alive` 保活注释 | 保活仍按官方文档实现（忽略注释行），由 `stream_keepalive_and_broken.sse` 覆盖该形态 |

### 4.2 追加观测：流式也会"只有思维链"

**2026-10-13 一次测评作答 `completion=411 reasoning=411`、HTTP 200、正文为空**（`max_tokens=8192`，未截断）。
同一批 53 次调用里出现 3 次。

### 4.3 样本维护

`recorded/` 下只记录模型输出与结构，**不得包含 API Key**
（由 `tests/test_recorded_fixtures.py::test_recorded_samples_contain_no_secrets` 强制守卫）。

## 6. 判据与观测的由来

### 6.1 为什么 `empty_content` 必须算失败

思考模式下模型有概率把输出预算全花在思维链上，正文一个字都不给——`completion=411 reasoning=411`，
且**与 `max_tokens` 无关**（远未顶到上限时也会发生），实测 53 次调用里出现 3 次。
它不会抛异常、HTTP 也是 200，所以在补上这条判定之前会被当成"成功"：落一条空回复、返回 200，
界面上用户提交完回答后什么都不显示，看着像卡死。

两条防线：

1. 客户端在整条流没有任何正文时按可重试错误处理（**思维链不算正文**，因为它不是用户要的答案）；
2. 执行器在组装后的正文为空（含只有空白）时**绝不下库**，返回可重试失败——重试已经试过一轮
   还能走到这里，说明模型确实什么都没给。

`empty_content` 与 `protocol` 的区别：前者是"模型自己没说话"，后者是"响应结构对不上"。
**结构化输出通道**对空内容的处理更早：它会把 `max_tokens` 翻倍后重试一次，
所以 JSON 场景下这条链路通常不会冒到用户面前。

### 6.2 为什么测评的一轮必须原子

早期实现把作答与轮次计数放在调用模型**之前**落库，失败也不回退。失败后对话最后一条变成用户的作答，
而 `pending_question` 由"最后一条 assistant 消息"推出 → 它变成 `null`、提交按钮点不动。
用户既看不到问题、也重试不了，只能放弃整次测评。

修法：作答与轮次计数推迟到整轮成功之后，失败用 `Memory.snapshot()` / `replace_with()` 整体回退。

### 6.3 `hit_points` 为什么必须可见

`pass` 的依据必须可见，否则无法发现"放水"：判定器说通过，却说不清命中了哪些要点。
后端在 `pass` 但 `hit_points` 为空（或同时给出 `missing_points`）时自动降级为 `partial`，
并在 `feedback` 末尾追加说明。

## 7. 维护约定

1. **契约升版**：先在本文追加"变更摘要"，再更新 [接口契约](接口契约.md) 的当前内容；
   两侧的版本号必须一致。
2. **新增列**：同时登记到 `_COLUMN_UPGRADES`，否则老库运行期报 "no such column"。
3. **新增/修改事件或字段**：必须检查前端与既有数据的兼容性；破坏性变更需单独立节说明迁移方式
   （截至 v1.6 尚未出现）。
4. **录制样本**：重新录制后，若实测事实发生变化，更新本文 §4 并在当前契约中同步受影响的解析约定。
