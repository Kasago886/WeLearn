## 1. 下行事件契约（后端 → 前端）

传输：`text/event-stream`，每帧形如

```text
event: token
data: {"text":"北"}
```

| 事件 | 载荷字段 | 发送时机 | 关联需求 |
| --- | --- | --- | --- |
| `token` | `text` | 正文增量（流式，可多次） | FR-401, FR-412 |
| `reasoning` | `text` | 思维链增量（流式，前端默认折叠，可通过 `show_reasoning` 关闭） | FR-713 |
| `verdict` | `verdict` / `confidence` / `feedback` / `hit_points` / `missing_points` | 检查点判定完成 | FR-404 |
| `node_state` | `node_id` / `state` / `index` / `total` | 节点状态变更 | FR-309, FR-408 |
| `assessment` | `status` / `topics` / `turn_number` / `total_turns` / `current_topic` / `profile` | 测评一次交互结束（首问、后续提问、画像、跳过） | FR-201, FR-202, FR-205, FR-206 |
| `path` | `path_id` / `version` / `rationale` / `nodes[]` | 学习路径生成完成 | FR-301, FR-308 |
| `options` | `kind` / `choices` / `message` / `directions` | 需要用户做出选择（重试耗尽后的三选一） | FR-408 |
| `hint` | `level` / `label` / `question` | 给出了一级提示（v1.2 新增） | FR-407 |
| `error` | `category` / `message` / `retryable` | 出现可操作错误 | FR-709, FR-712 |
| `done` | `conversation_id` / `usage` | 一轮结束（含用量） | FR-705 |

`verdict` 取值：`pass` / `partial` / `fail`。
`node_state` 取值：`not_started` / `learning` / `mastered` / `partial` / `skipped` / `review_needed`。
`assessment.status` 取值：`question`（提问）/ `profile`（画像已产出）/ `skipped`（用户跳过测评）。
`options.kind` 取值：`exhausted`（单节点重试已耗尽，三项选择 `reteach` / `show_answer` / `advance`）。
`hint.level` 取值：`1`（方向性提示）/ `2`（关键要素提示）/ `3`（近似答案）；
`hint.label` 是对应的中文名，前端直接展示即可，不必自己维护映射表。

**`path` 事件里的 `nodes[]`**：`id` / `index` / `title` / `objective` / `key_points` / `state` /
`is_quick_review` / `checkpoints[]`（`id` / `question`）。`rationale` 是"为什么这样安排"的说明，
必须在路径页展示（FR-302）。

**`assessment` 事件的 `profile`**（仅当 `status = profile` 时非 `null`）：`levels[]`
（`topic` / `level` / `evidence`）/ `summary` / `suggested_start_node`。

### 1.1 节点位置约定（v1.1 明确）

`node_state.index`、路径里 `nodes[].index`、`current_index` **一律从 1 开始**，
与 UI 上的"第 2/4 个节点"一致；需要 0 基下标时请用数组顺序，不要用这些字段减一。
`total` 为路径节点总数。`current_index` 指向第一个尚未完成的节点，全部完成时指向最后一个节点
（是否真正完成以 `completed` 为准）。

`node_state` 描述的是**本轮结束时用户所在的节点**：进入节点时为 `learning`（FR-309）、
判定通过为 `mastered`、重试耗尽后选择"查看参考答案"为 `partial`、
选择"直接进入下一节点"则报出**下一个节点**（`not_started`，会话同时落到该节点上）。

### 1.2 刷新恢复的数据来源（P2B 明确）

前端刷新后不需要自己拼状态，契约里已经给了三份数据：

| 场景 | 恢复依据 |
| --- | --- |
| 该显示哪一步 | `GET /state` 的 `session.next_action`（`assess` / `confirm_path` / `teach` / `answer` / `decide` / `completed` / `paused`） |
| 测评中：正在问什么 | `GET /assessment` 的 `transcript` + `pending_question`（测评记忆里的问答正文） |
| 教学中：问过什么、判过什么 | `GET /teach/current` 的 `pending_question` + `answers`（`answer_record` 全量记录） |

**为什么教学的讲解正文不在恢复范围内**：它存在于对话记忆里、可以被重新生成，
而作答记录是用户自己的输入，丢了就找不回来——恢复的优先级按"不可再生"排序。

**前端必须遵守的两条约定**：

1. `error` 的 `message` 是**面向用户的可操作文案**，不得显示原始异常或响应体；
2. `done` 之后本轮结束，客户端不得再等待更多事件；`retryable=true` 的错误才展示"重试"入口。

**错误分类（`error.category` 取值）**：`busy`（正在生成，AC-17）、`config`、`auth`、`balance`、
`rate_limit`、`server_error`、`unavailable`、`timeout`、`network`、`bad_request`、`invalid_params`、
`protocol`、`empty_content`（v1.3 新增）、`unknown`。其中 `busy` 由后端调度器产生（FR-611：明确拒绝而非静默丢弃）。

**判定降级语义**：若模型把 `verdict` 判为 `pass` 却未给出 `hit_points`（或同时给出 `missing_points`），
后端会**自动降级为 `partial`** 并在 `feedback` 末尾追加说明（FR-404）。前端无需感知该逻辑，
但不得假定"模型说 pass 就一定收到 pass"。

**`hit_points` 为 T1.6 新增字段**：v1.0 冻结时遗漏，P1 实现判定器时补入（`pass` 的依据必须可见，
否则无法发现"放水"）。

对应代码：`app/contracts/events.py`（`SseEventType`、各 payload 模型、`encode_frame`）。

## 2. 结构化输出契约（模型 → 后端）

统一要求（FR-716）：

1. 请求设置 `response_format = {"type":"json_object"}`；
2. 提示词中**必须出现 `json` 字样**并给出输出样例；
3. **必须显式设置 `max_tokens`**，否则 JSON 可能被截断；
4. 必须处理官方已知的"返回空 `content`"：解析失败或为空时重试一次，重试仍失败给出可重试错误，且不得污染会话状态。

| 用途 | JSON 结构（摘要） | 硬约束（违反即构造失败） | 关联需求 |
| --- | --- | --- | --- |
| 测评画像 | `{"levels":[{"topic","level","evidence"}],"summary","suggested_start_node"}` | `level ∈ {none,basic,proficient}`；`levels` 1~12 项 | FR-206 |
| 路径规划 | `{"rationale","nodes":[{"title","objective","prerequisites","key_points","checkpoints":[{"question","expected_points","reference_answer"}]}]}` | `nodes` 3~15 个；每个节点 `key_points` 3~6 条、`checkpoints` ≥1 个且 `expected_points` 非空 | FR-301, FR-302 |
| 判定 | `{"verdict","confidence","feedback","hit_points","missing_points"}` | `verdict ∈ {pass,partial,fail}`；`confidence ∈ [0,1]`；**`pass` 必须给出非空 `hit_points`**，否则判定器自动降级为 `partial` | FR-404, FR-405 |
| 压缩摘要 | `{"compressed_context":"..."}` | 空串表示无需保留（`Empty`，不重试） | FR-605, FR-607 |

对应代码：`app/contracts/schemas.py`。解析容错规则见需求规格说明书 FR-607（严格 JSON → 去 markdown 包裹 → 截取最外层 `{}`）。

## 3. 上游请求契约（后端 → DeepSeek）

端点：`POST {base_url}/chat/completions`；`base_url` 保留子路径（如 `/v1`）。

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `model` | `deepseek-flash`（默认）/ `deepseek-v4-pro` | 旧名 `deepseek-v4-flash`、`deepseek-v4-flash-vision-exp` 仍可调用，但官方会映射到 DeepSeek-V4.1-Flash 并按 Flash 计价（FR-702） |
| `messages` | 协议消息数组 | 消息以原始字段字典承载，保留服务端附加字段（FR-603） |
| `stream` | `true` / `false` | 流式用于教学与测评 |
| `thinking` | `{"type":"enabled"｜"disabled"}` | 官方默认开启（FR-717） |
| `reasoning_effort` | `low` / `high` / `max` | 仅思考开启时下发；官方默认 `high` |
| `max_tokens` | 正整数 | JSON Output 场景必须下发（FR-716） |
| `response_format` | `{"type":"json_object"}` | 仅结构化输出场景下发 |
| `tools` | 工具数组 | **仅在确有工具时下发**，避免部分端点不接受 `"tools": null` |

**官方限制（由上层保证）**：思考模式下不支持 `tool_choice=required` 与指定具体 tool（返回 400，FR-714）；
思考模式下 `temperature`/`presence_penalty`/`frequency_penalty` 不生效、`top_p` 被钳制到 `0.95`–`1.0`（FR-718）；
携带 `tools` 时历史 `reasoning_content` 必须回传并会拼进上下文（FR-719）。

对应代码：`app/infra/deepseek/protocol.py`。

## 4. 错误分类契约

| 状态码 / 情形 | `category` | 可重试 | 面向用户的提示 |
| --- | --- | --- | --- |
| 400 | `bad_request` | 否 | 请求体格式错误，请检查模型名与消息结构后重试。 |
| 401 | `auth` | 否 | API Key 无效或未授权，请在设置中更新 Key。 |
| 402 | `balance` | 否 | 账户余额不足，请充值后重试。 |
| 422 | `invalid_params` | 否 | 请求参数错误，请检查模型名与参数取值。 |
| 429 | `rate_limit` | 是 | 请求速率达到上限，稍后会自动重试。 |
| 500 | `server_error` | 是 | DeepSeek 服务器故障，稍后会自动重试。 |
| 503 | `unavailable` | 是 | DeepSeek 服务器繁忙，稍后会自动重试。 |
| 超时 | `timeout` | 是 | 请求超时，可点击重试或调大超时时间。 |
| 网络中断 / 服务端在 10 分钟未开始推理时关闭连接 | `network` | 是 | 网络连接中断，请检查网络后重试。 |
| 配置缺失（未配 Key / base_url / model） | `config` | 否 | 按缺失项给出具体引导 |
| 响应结构不符 | `protocol` | 否 | 响应无法解析，请查看日志 |
| 模型只输出思维链、正文为空 | `empty_content` | 是 | 模型这次只给出了思考过程、没有给出正文，已自动重试。请再点一次。（v1.3 新增） |

**重试边界**：默认最多 2 次、指数退避，分两种情况。

- **吐过正文再失败 → 直接上报**（FR-412）：重试会让同一段话在界面上出现两次；
- **一个字正文都没吐出来 → 允许重试**，包括下面这种"静默失败"。

**`empty_content` 为什么必须算失败**（2026-10-13 真实观测，v1.3 补入）：思考模式下模型有概率把
输出预算全花在思维链上，正文一个字都不给——`completion=411 reasoning=411`，且**与 `max_tokens`
无关**（远未顶到上限时也会发生），实测 53 次调用里出现 3 次。它不会抛异常、HTTP 也是 200，
所以在补上这条判定之前会被当成"成功"：落一条空回复、返回 200，界面上用户提交完回答后
什么都不显示，看着像卡死。

两条防线：

1. 客户端在整条流没有任何正文时按可重试错误处理（**思维链不算正文**，因为它不是用户要的答案）；
2. 执行器在组装后的正文为空（含只有空白）时**绝不下库**，返回可重试失败——重试已经试过一轮
   还能走到这里，说明模型确实什么都没给。

`empty_content` 与 `protocol` 的区别：前者是"模型自己没说话"，后者是"响应结构对不上"。
注意**结构化输出通道**（§2）对空内容的处理更早：它会把 `max_tokens` 翻倍后重试一次，
所以 JSON 场景下这条链路通常不会冒到用户面前。

对应代码：`app/infra/deepseek/errors.py`、`app/infra/deepseek/client.py`、`app/services/llm/agent.py`。

## 5. 数据库表结构

时间戳统一存 UTC（展示时转本地）。已落地（T0.3）：

| 表 | 主键 | 关键列 | 说明 |
| --- | --- | --- | --- |
| `schema_version` | `version` | `applied_at` | 轻量迁移记录（见待决策项 E2） |
| `app_settings` | `id`（恒 1） | 全部业务列可空 | 列缺失/非法即回退默认（FR-902） |
| `api_key_secret` | `id`（恒 1） | `cipher`、`masked_hint`、`source` | 只存密文（FR-708） |
| `conversation` | `id`（uuid） | `kind`、`subject_id`、`round_count`、`compressed_at` | 记忆容器，测评/教学/复习各一条（FR-602） |
| `chat_round` | `id` | `conversation_id`、`round_index` | 唯一索引 `(conversation_id, round_index)` |
| `message` | `id` | `role`、`content`、`reasoning_content`、`tool_calls_json`、`is_summary` | 摘要消息标记 `is_summary` |
| `usage_record` | `id` | `purpose`、`model`、`prompt/cached/miss/completion/reasoning/total tokens` | 命中与未命中都记录（FR-705） |

**领域表（v2 已落地）**：`subject`、`session_state`、`assessment`、`assessment_level`、`learning_path`、
`knowledge_point`、`checkpoint`、`answer_record`、`weak_point`、`study_note`（字段与取值约束见
需求规格说明书第 6 章与 `app/infra/storage/models.py`）。要点：

| 表 | 关键约束 |
| --- | --- |
| `subject` | `status` 与 `session_state.state` 同源；`archived` 决定列表可见性（FR-103、FR-106） |
| `session_state` | 每个主题恒一行；`state` 迁移受状态机白名单约束（FR-410） |
| `assessment` | 进行中的测评每个主题至多一条（`get_running`） |
| `learning_path` | 同一主题只有一条 `is_active = 1`（FR-308） |
| `knowledge_point` | `state` 覆盖 `not_started/learning/mastered/partial/skipped/review_needed`（FR-309） |
| `answer_record` | 每次判定落一条；`verdict` + `hit_points`/`missing_points` 使"放水"可追溯（FR-404） |
| `weak_point` | `reason ∈ {partial, skipped, show_answer, advanced}`（FR-409 的语义区分） |

**v3 列级增量升级**：`session_state.awaiting_decision`（表示"等用户三选一"）。
**v4 列级增量升级（P3A）**：

| 表 | 列 | 用途 |
| --- | --- | --- |
| `session_state` | `last_action` | 最近一次教学动作（`explain` / `reteach:simpler` / `hint:2` / `reference`），供"重新生成上一条回复"知道该重跑什么（FR-413） |
| `message` | `kind` | 消息用途标记；`off_topic` 表示穿插提问（FR-411），用于把主线与随口提问分开 |

**v5 列级增量升级（P3B）**：

| 表 | 列 | 用途 |
| --- | --- | --- |
| `answer_record` | `source` | `teach` / `review`（FR-507）。**带 `DEFAULT 'teach'`**：v5 之前所有作答都来自教学，升级时必须回填，否则老记录会是 `NULL`，档案页据此分类就会漏掉它们 |
| `usage_record` | `duration_ms` | 单次模型调用耗时，完成报告统计"累计耗时"用（FR-417）。老记录留空——不编一个 0 出来 |
| `session_state` | `review_mode` / `review_node_id` / `review_checkpoint_id` | 进行中的复习会话。**与教学字段分开存**：复习某个旧节点时若复用 `current_node_id`，用户回到教学页会发现自己"跳"到了那个旧节点上 |
| `session_state` | `adjacent_review_for` | 为进入哪个节点已经做过"回顾上一节点"（FR-414）。没有它，用户刷新后点「继续学习」会被重复问一遍上一节点 |

**v6 列级增量升级（P3C，均在 `app_settings`）**：

| 列 | 用途 |
| --- | --- |
| `temperature` / `top_p` | 采样参数（FR-718）。老库回填默认值 1.0 / 1.0，行为与升级前一致（此前不下发这两个参数） |
| `audit_enabled` | 请求审计开关（FR-715），默认关闭；此前只有环境变量 `WELEARN_LOG_LLM_PAYLOAD` 能打开 |
| `use_recommended_overrides` | 启用推荐组合（FR-703），默认关闭 |
| `purpose_overrides_json` | 逐用途覆盖（FR-703），存 JSON 文本；解析失败一律回退为"继承全局"，绝不让设置读取抛异常 |

SQLAlchemy 的 `create_all` **不会**修改已存在的表，因此 `app/infra/storage/db.py` 在 `init()` 中按
`SCHEMA_VERSION = 6` 执行幂等的列升级（先 `PRAGMA table_info` 检查，再 `ALTER TABLE ADD COLUMN`）。
新增列时必须同时登记到 `_COLUMN_UPGRADES`，否则老库升级后会在运行期报"no such column"。
`tests/test_schema_upgrade.py` 用"手工建一张缺列的旧表"复现该场景。

> 说明：`conversation.subject_id`、`usage_record.subject_id`/`conversation_id` 暂用字符串外键，
> 待 `subject` 表落地后再补外键约束，避免"先建表后改约束"的迁移负担
> （`subject` 已落地，但外键补齐属于 T3.x 的迁移工作，P2 不引入）。

## 6. HTTP 接口

### 6.1 通用约定

- 前缀 `/api`；**无鉴权**（单用户自托管，NFR-101/102）；
- 请求体与响应体均为 JSON（`{subject_id}` 为 uuid 字符串）；
- 响应中**永不含 API Key 明文或密文**，只有掩码（FR-708）；
- 错误响应统一为 `{"detail": "面向用户的中文说明"}`：
  - `404`：主题/子领域不存在；
  - `409`：请求本身合法但**当前状态不允许**（未生成路径就确认、还没进入教学就暂停/继续、非法状态迁移）；
  - `422`：入参校验失败（pydantic）或主题输入不合法（FR-102）；
- **流式端点**（下表标 ★）返回 `text/event-stream`，载荷见 §1。流式端点**一律返回 200**，
  业务错误通过 `error` 事件表达；只有"主题不存在"这类请求级错误才在建立流之前抛 404。

**复习产出（`/review/start`、`/review/answer` 的响应，`GET /review` 的 `current` 同形）**：

```
{ text, phase, mode, node, verdict, confidence, feedback,
  hit_points[], missing_points[], promoted, resolved,
  fail_count, suggestion, node_index, node_total }
```

- `phase`：`question`（待作答）/ `passed`（通过）/ `failed`（未通过）
- `mode`：`weak`（薄弱点复习）/ `adjacent`（进入新节点前的回顾）
- `promoted` + `resolved` 同时为真表示"节点已升级 + 薄弱点已解除"
- 错误：请求合法但当前状态不允许 → **409**（与路径编辑、教学门禁一致）

**`/teach/current` 的 `review` 字段**（FR-414）：正在等一次"回顾上一节点"的作答时为
`{"mode":"adjacent","node_id","node_title","question"}`，否则为 `null`。前端据此把
"这次不是检查点作答"讲清楚——否则用户会以为系统问错了题。

**`source` 字段**：`answer_record` 与节点笔记都带 `source`。作答的 `source` 为
`teach` / `review`（FR-507），笔记为 `auto` / `user`（FR-801）。档案页据此区分来源。

**6.2.2 模型策略、审计与运维可见性（v1.5 新增）**

`GET` / `PUT /api/settings` 在既有字段之外新增：

| 字段 | 取值 | 用途 |
| --- | --- | --- |
| `temperature` | 0~2，默认 1.0 | 采样温度（FR-718）；**思考模式下官方忽略它** |
| `top_p` | 0.01~1，默认 1.0 | 核采样（FR-718）；**仅思考模式生效，且被钳制到 0.95~1.0** |
| `audit_enabled` | bool，默认 `false` | 请求审计开关（FR-715）：记录完整请求与响应，Key 始终脱敏 |
| `use_recommended_overrides` | bool，默认 `false` | 启用推荐组合（FR-703）：规划/判定用深度模型 + `high`，压缩关闭思考 |
| `purpose_overrides` | 对象，见下 | 逐用途覆盖，优先级高于推荐组合 |
| `model_plan` | 对象，**只读** | 每个用途解析后的实际参数，前端据此证明"覆盖真的生效了" |

`purpose_overrides` 的形状（键即 `LlmPurpose`，缺省或非法一律回退为"继承全局"）：

```json
{ "judge": { "model": "pro", "thinking": "inherit", "reasoning_effort": "high" } }
```

- `model`：`inherit` / `default`（默认模型） / `pro`（深度模型）
- `thinking`：`inherit` / `on` / `off`
- `reasoning_effort`：`inherit` / `low` / `high` / `max`

`model_plan` 的形状：

```json
{ "judge": { "model": "deepseek-v4-pro", "thinking": true, "reasoning_effort": "high" } }
```

`GET /api/usage` 在既有字段之外新增（旧字段全部保留）：

| 字段 | 说明 |
| --- | --- |
| `duration_ms` | 累计模型调用耗时（毫秒）；老记录留空按 0 计 |
| `by_purpose` | `{用途: {calls, prompt_tokens, cached_prompt_tokens, cache_miss_tokens, completion_tokens, reasoning_tokens, total_tokens, cache_hit_rate, duration_ms}}` |
| `by_subject` | 按总 token 降序前 10：`[{subject_id, title, calls, total_tokens, cache_hit_rate, duration_ms}]` |
| `cache_hint` | 命中率异常（有调用但命中率为 0）时的中文排查提示，正常为 `null`（FR-705、FR-720） |

`GET /api/health`（FR-909）新增 `storage.writable`、`logs{dir,level,writable}`、
`llm{audit_enabled,configured}`、`usage{calls,total_tokens,cache_hit_rate}`、
`features{use_recommended_overrides,show_reasoning,thinking_enabled}`；数据目录或日志目录不可写时
`status` 降级为 `degraded` 并把 `data_dir` / `logs` 计入 `problems`。原有字段一律不变。

## 8. 真实样本验证结论（2026-10-10 录制）

录制命令：`python scripts/llm_smoke.py --record`（模型 `deepseek-flash`，思考开启，`effort=high`）。
回放测试见 `tests/test_recorded_fixtures.py`。以下为实测确认的事实，实现已与之对齐：

| # | 实测事实 | 对实现的影响 |
| --- | --- | --- |
| 1 | 数据块除 `choices` 外还带 `object` / `created` / `system_fingerprint`，`choices[0]` 还带 `logprobs` | 解析器只读 `choices[0].delta`，必须忽略未知字段（已满足） |
| 2 | 首块 `delta` 为 `{role:"assistant", content:null, reasoning_content:""}`，后续块也会出现空串 | 空串必须按"无增量"丢弃，否则会向前端推大量空事件（已满足） |
| 3 | 思维链与正文在 `delta` 中**交替**到达（本次 235 个思维链碎片、92 个正文碎片） | 前端需分别渲染两路增量；`reasoning` 与 `token` 事件不可合并 |
| 4 | 用量只在最后一个数据块出现：`prompt=40, cached=0, miss=40, completion=328, reasoning=235, total=368` | 收尾事件 `done` 必须携带该用量；首次调用的 `cached=0` 属正常（尚无缓存前缀） |
| 5 | JSON Output 返回 `{"answer": "..."}`，可用 `json.loads` 直接解析；关闭思考时 `reasoning_content` 为空串 | 结构化输出通道可行；空思维链按 `None` 处理 |
| 6 | `GET /models` 返回 `deepseek-flash`（DeepSeek-V4.1-Flash）与 `deepseek-v4-pro`，`context_window=1048576`、`max_output_tokens=393216`、`effort.supported_levels=[low,high,max]`、`default_level=high` | 与官方文档一致；设置页可据此渲染档位，不必写死（FR-702、FR-717） |
